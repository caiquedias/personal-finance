## Decisões técnicas
- Entidade `UserToken` separada (padrão `MfaRecoveryCode`); `UserToken.IsInvalidated` guarda "limite de tentativas atingido" (a 3ª falha invalida; `RegisterFailedAttempt(max)` não recebe `now`)
- Código de 6 dígitos para reset e verificação; HMAC com chave do servidor (`Auth:UserTokens:HmacKey`, Base64 de 32 bytes, sempre validada no startup); sem salt em coluna — o hash é preso ao contexto `tokenId|userId|purpose|código`
- 3 tentativas, TTL 10 min, cooldown 60 s por conta; concorrência no contador via `RowVersion` + retry em `ConcurrencyConflictException`; hard delete dos tokens anteriores a cada emissão
- Endpoints anônimos com resposta genérica; código inválido/expirado → 400, nunca 401 (o `authInterceptor` faz logout em 401); register passa a 202 genérico (fecha a enumeração de e-mail)
- Envio em fila (`Channel` limitado 1000, `DropWrite`) + `EmailDispatchHostedService`; Brevo via API HTTP atrás de `IEmailSender` (sem pacote novo); `Email:Enabled=false` só loga destinatário e assunto
- Link do e-mail: `{App:FrontendBaseUrl}/reset-password#email=...` — fragmento não vai ao servidor/Referer; código só no corpo; host só da config (nunca do header Host)
- Login com `Enforce` (default `false`) + backfill de `EmailConfirmedAt` na migration; reset concluído confirma o e-mail e zera o lockout
- Ciclo de correção pós-Reviewer: Brevo validado no startup só com `Enabled=true` + timeout 15 s (`EmailOptions`/`BrevoOptions` em options pattern lazy); `UserTokenIssuer` captura só `ConcurrencyConflictException` (corrida → 202 genérico, sem 409); complete/confirm fazem HMAC + `GetLatestAsync(Guid.Empty, …)` dummy para usuário inexistente/inativo/removido (equalização aproximada)

## Análise de eficiência da sessão
- **Estimativa:** 3h (gerada pelo PO nesta sessão, após 3 rodadas de análise)
- **Duração de codificação:** 31min (Red 13:02 → último Green 13:34, antes do ciclo de correção; o agente Red rodou 30min antes do primeiro commit, então Red→Green em tempo real ≈ 1h02)
- **Duração de sessão completa:** 2h38min (primeiro commit 12:34 ao último 15:13; inclui o ciclo de correção e QA/UX/Reviewer; sem as rodadas de planning anteriores ao 1º commit) | **Desvio vs. Estimativa:** dentro do estimado (-12%)
- **Ciclos de retrabalho:** 1 (QA: 0 | Reviewer: 1 — veredito APROVADO com 3 itens MÉDIA que o Caique mandou corrigir; QA e Reviewer revalidaram sem nova correção)
- **Causas identificadas:**
  - `BrevoOptions` sem validação nem timeout: a task 5 adiou a validação para a 11 e o contexto não pedia validar nem limitar o provedor externo
  - `UserTokenIssuer` sem tratamento de `ConcurrencyConflictException`: o contexto previa retry só no contador de tentativas, não no commit dos fluxos anti-enumeração (forgot/resend/register)
  - Timing do complete/confirm: o Red exigiu `Hash` Never para usuário inexistente e o contexto não pedia equalizar o resto do caminho
  - Escopo cresceu de ~20 para 112 arquivos ao longo do planning (3 rodadas do PO); o 1º Red custou 386.725 tokens (maior gasto)
  - Compile-red fez o Green mover testes para o scratchpad para validar; uma vez o `mv` de volta foi negado e a restauração foi por `git checkout`; o Red reescreveu mensagens de commit com `filter-branch`
- **Melhorias propostas:**
  - PO incluir na Análise de Impacto, quando a issue integra provedor externo, o item "validar options no startup + timeout do HttpClient"
  - Contexto compartilhado exigir, para fluxos anti-enumeração, que todo commit trate `ConcurrencyConflictException` com resposta genérica
  - Red/Green: proibir reescrever histórico (`filter-branch`/`rebase`/`amend`) e mover arquivos de teste — dividir o Red por camada em branches compiláveis ou aceitar o build só no último Green
  - Abrir issue de tooling (S) para blindar os testes de startup (`[Collection]` + `DisableParallelization`) contra o flaky
