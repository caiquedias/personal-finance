## Decisões técnicas
- `Income.Update` e `IIncomeRepository.GetByIdAndUserAsync`/`UpdateAsync` já existiam no Domain (usados pelo `ImportLegacyDataUseCase` do import legado) — nenhuma alteração em Domain nesta issue.
- `PeriodId` fica fora do `UpdateIncomeDto` propositalmente — período é imutável no update, reforçado em 3 camadas: DTO backend não aceita o campo, `FormControl` desabilitado no Angular, hint visual no HTML.
- Erros de ownership/not-found retornam 400 (`DomainException`), nunca 404 — mesmo padrão já usado no `UpdateExpenseUseCase`/`ExpensesController` (não é regressão desta issue; o `[ProducesResponseType(404)]` do controller ficou documentado incorretamente, mas é debt pré-existente, mesmo do Expense).
- Não foi criado FluentValidation validator novo — validação de negócio (amount > 0, descrição não vazia) é feita no Domain via exceções, mesmo padrão do `UpdateExpenseDto`.

## Desvios do spec
- Sizing original da issue era S (~6-8 arquivos); análise de impacto do PO ajustou para M (13 arquivos) por incluir também o registro de DI (não mencionado na issue) e o CSS de contraste do estado disabled (achado do UX Validator, fora do escopo original).
- O texto da issue descrevia "form de edição no incomes.component" como se fosse novo — na prática o modal de edição já existia; o trabalho real foi trocar a lógica de submit de `deleteIncome+createIncome` (não atômico) para `updateIncome` real.
